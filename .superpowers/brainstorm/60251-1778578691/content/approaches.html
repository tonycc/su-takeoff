三种实现方案对比

核心问题：统计数据（MaterialUsage）没有面级细节和组件层级，如何构建组件树？

A

Ruby 端同时传回 ScanItem + MaterialUsage

在 finalize_and_compute 中额外发送 @last_scan[:items] 到前端，前端在 Phase 3 用 component_path 构建树，用 items 汇总统计，用 MaterialUsage 显示采购量

Pros

  • 数据完整，面级信息丰富
  • 可复用 Phase 1 已有的树形渲染逻辑（toggleGroup）
  • MaterialUsage 提供采购量等计算结果

Cons

  • 数据量大（大模型可能有数百面）
  • 前后端都需要改：Ruby 多传数据，JS 新增视图
B

Ruby 端构建组件树结构，前端直接渲染

新增 Ruby 方法将 ScanItem + MaterialUsage 合并构建嵌套树结构 {name, children, faces, stats}，前端只需递归渲染

Pros

  • 前端逻辑简单，只负责渲染
  • 树结构可复用（后续可导出为 JSON/CSV）

Cons

  • Ruby 端多了树构建逻辑
  • 数据结构与 UI 展示耦合
C

Phase 1 缓存的 ScanItem 在 Phase 3 复用

Phase 1 已经传了所有 ScanItem 到 JS（存在 window._reviewState.items）。Phase 3 直接用缓存数据 + MaterialUsage 构建组件树

Pros

  • Ruby 端零改动
  • 不增加数据传输量

Cons

  • 依赖全局状态，用户切标签页后可能丢失
  • 去重后的面不一致：Calculator 做了薄板去重，但缓存里是去重前的面
  • 数据完整性依赖 Phase 1 状态
