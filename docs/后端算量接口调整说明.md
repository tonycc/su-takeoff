# 后端算量接口调整说明

本文对应当前 SU 插件推送接口 `POST /api/v1/su/quantities`。插件现在会把组件级项目产品关联一起推送，后端需要按以下契约调整。

## 1. Component 增加项目产品 ID

项目产品关联按组件定义名保存，推送时放在 `components[]` 级别。当前插件复用“按组件”页面的最终行，只推送确认推送时页面可见的群组/组件树节点（包括四个数量列都显示 `-` 的组件）；不推送模型根、具体面和折叠状态下不可见的子级组件。无数量组件通过 `parts: []` 传输：

```json
{
  "code": "c-abc123",
  "name": "橱柜",
  "component_type": "component_instance",
  "quantity_tag": "按面积+个数",
  "project_product_id": "project-product-uuid",
  "parts": [
    {"code": "p-abc123", "name": "面积", "quantity": 2.5, "unit": "m2"},
    {"code": "p-def456", "name": "长度", "quantity": 10.64, "unit": "m"}
  ]
}
```

字段要求：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `quantity_tag` | string | 否 | 组件当前选择的算量标签；复合标签作为一个整体字符串保存，未选择时插件不发送 |
| `project_product_id` | string | 否 | `projects_project_products.id`，未选择产品时不发送 |

该字段建议保持可选，以兼容尚未升级的旧插件和未选择项目产品的组件。

## 2. 请求 Schema

后端 `SuQuantityComponent` 增加：

```python
project_product_id: str | None = Field(default=None, max_length=36)
```

当前插件不发送 `faces[]`；`SuQuantityFace` 可以保留用于旧客户端兼容。插件发送的页面计量 `parts[]` 没有 `material_tag`，因此入口 Schema 应允许缺省：

```python
class SuQuantityFace(BaseModel):
    code: str = Field(min_length=1, max_length=128)
    material_tag: str | None = Field(default=None, max_length=128)
    area_m2: Decimal


class SuQuantityPart(BaseModel):
    code: str = Field(min_length=1, max_length=128)
    name: str = Field(max_length=256)
    quantity: Decimal
    unit: str = Field(min_length=1, max_length=16)
    material_tag: str | None = Field(default=None, max_length=128)
```

## 3. 入库和归属校验

`quantities_components` 增加可空字段：

```text
project_product_id VARCHAR(36) NULL
```

可选地建立到 `projects_project_products.id` 的外键。入库前必须校验：

1. 项目产品 ID 存在；
2. 项目产品属于当前租户；
3. 项目产品所属项目与 `payload.project.code` 一致；
4. 项目产品未被删除或停用。

不满足时返回 `422 INVALID_PROJECT_PRODUCT`，不要返回数据库异常。

如果暂时不做数据库迁移，也可以先在服务层保存到 JSON 扩展字段，但正式版本建议落到 `quantities_components.project_product_id`。

## 4. 页面计量列兼容

插件通过 `components[].quantity_tag` 发送组件当前选择的算量标签，同时使用标签更新后的页面最终值。后端应按 `parts[].name/unit` 识别四个页面计量列：`面积/m2`、`长度/m`、`体积/m3`、`件数/个`。未选择标签的组件不携带 `quantity_tag`，后端可根据 `parts` 兼容推导展示标签。

标签名称原样传递，复合标签（例如 `按面积+个数`）不拆分。

## 5. 材料标签兼容

当前插件的 `parts[].name` 是页面计量列名称（面积/长度/体积/件数），不是 SU 材质名；插件不发送具体面，也不发送 `material_tag`。若数据库仍要求 `material_tag` 非空，建议服务层使用：

```python
MISSING_MATERIAL_TAG = "未指定材质"

part_material_tag = part_data.material_tag or MISSING_MATERIAL_TAG
```

`未指定材质` 不应自动匹配 SKU；项目产品关联使用组件级 `project_product_id`。

## 6. 幂等和版本

插件会把 `project_product_id` 放入组件业务内容后重新计算 `payload_hash`、`source_version` 和 `idempotency_key`。

因此同一组件更换项目产品后，会生成新的模型版本；同一产品重复推送仍保持幂等。

## 7. 当前插件不会发送的字段

后端不要将以下字段设为算量推送必填：

- `project_id`：插件推送中使用 `project.code` 和 `project.name`；
- `openings`：洞口面积已经从面积部品中扣除；
- `definition_name`：只用于插件本地映射，不进入当前 Payload；
- `product_id`、`catalog_code`、`product_name`、`project_product_code`：当前只推送 `project_product_id`；
- `faces`、`parent_id`、面定位路径、SketchUp `entityID`；
- `resolved_method`、`strategy_name`、宽高和图层等调试字段。

组件编码和部品编码均为插件生成的稳定字符串哈希，后端按字符串保存，不要解析为数字 ID。

## 8. 推荐成功响应

保持现有响应格式：

```json
{
  "sheet_id": "quantity-sheet-uuid",
  "model_version_id": "quantity-model-version-uuid"
}
```

如果管理端返回组件详情，建议同时返回：

```json
{
  "component_code": "c-abc123",
  "project_product_id": "project-product-uuid"
}
```

## 9. 推送版本信息（本次调整）

插件点击「推送算量」后会先要求用户填写版本号和更新内容，确认后才构建并发送 Payload。新增顶层字段：

```json
{
  "designer_account": "designer@example.com",
  "model_version_no": "V2026.08.05",
  "update_content": "调整卫生间龙头数量并补充灯具"
}
```

字段要求：

| 字段 | 类型 | 必填 | 长度 | 说明 |
| --- | --- | --- | --- | --- |
| `designer_account` | string | 是 | - | 当前登录设计师账号；插件从登录会话带入，不发送密码或 Token |
| `model_version_no` | string | 否 | 1~64 | 用户填写的模型版本号；不要映射为后端自动递增的 `version_no` |
| `update_content` | string | 否 | 1~2000 | 本次算量更新说明 |

后端需要调整 `SuQuantityPayload` Schema，至少增加：

```python
designer_account: str = Field(min_length=1)
model_version_no: str | None = Field(default=None, min_length=1, max_length=64)
update_content: str | None = Field(default=None, min_length=1, max_length=2000)
```

字段必须保持可选，以兼容旧插件；新插件请求会传递这两个字段。后端应分别写入 `QuantityModelVersion.model_version_no` 和 `QuantityModelVersion.update_content`，不能写入后端自动递增的 `version_no`。同时建议保留完整 `payload_json`。

幂等处理必须保持：

1. `designer_account`、`model_version_no`、`update_content`、组件及页面计量数据共同决定 Payload hash。
2. 任一字段变化时，插件生成新的 `source_version` 和 `idempotency_key`，后端创建新的模型版本。
3. 相同字段和相同数据的网络重试使用原 key，后端返回已有模型版本，不重复插入。
4. 幂等命中响应建议增加 `idempotent: true`，便于插件区分“新建成功”和“重复请求已复用”；这不影响现有响应字段。
