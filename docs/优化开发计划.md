# SU Takeoff 优化开发计划

本文档规划后续优化方向，目标是把"算准"这件事做到位。每一项包含问题、方案、数据模型变更、代码位置、验收标准，按优先级 P0→P4 推进。

---

## 背景

当前实现是 SU 材质 → 一条 `MaterialUsage` 的 1:1 映射，公式固定为 `net_area * (1 + waste_rate)`。现实中装修用量的准确度受限于三个盲区：

1. **洞口未真正扣减**：洞口被识别但 `host_face_ids` 始终为空，母墙面算的是毛面积
2. **辅材/基层全丢**：一张墙砖面对应的"粘结剂、基层处理、填缝剂"等派生项没有进入报表
3. **线性与离散材料缺失**：踢脚线（米）、门窗灯具（个）完全不在统计范围内

参考 Quantifier Pro 的思路（见 `docs/QP对比分析.md`，如无则参照本文档"附录 A"），本计划围绕以上盲区展开。

---

## 优先级总览

| 优先级 | 项目 | 预计工时 | 准确度贡献 |
|---|---|---|---|
| P0 | 修复洞口扣减链路 | 0.5 天 | 墙面积立即去毛存净 |
| P1 | 派生项（ProcessLibrary 扩展为派生规则） | 2–3 天 | 覆盖基层/辅材，占缺口最大头 |
| P2 | 边长与实例计数通道 | 2 天 | 纳入线性材料与离散件 |
| P3 | 损耗率升级为表达式 | 1 天 | 支撑整砖向上取整等特殊规则 |
| P4 | 规则写入模型属性字典 | 1 天 | 团队协作一致性（非准确度） |

## P0：修复洞口扣减链路

### 问题

`scanner.rb:163/209/232` 在创建 `Opening` 时 `host_face_ids` 全部传 `[]`。`calculator.rb:28-34` 依赖该字段把洞口面积加到 `opening_area_by_face` 上；现在这张表总是空的，导致 `calculator.rb:82-86` 的扣减永远是 0。

### 方案

在 Scanner 识别出一个洞口面之后，反向查找与其共面且包含其包围盒的候选母面：

1. 候选池：同一容器（Group/ComponentInstance）内、法向量与洞口面接近平行（`|n1·n2| > 0.99`）、且 z 坐标（对墙面）或 x/y 坐标接近的面
2. 几何判定：洞口包围盒在候选母面所在平面上的投影是否被母面轮廓包含
3. 把被命中的母面 `entityID` 写入 `Opening.host_face_ids`

### 数据模型变更

无。`Opening` 结构体字段保持不变。

### 代码位置

- `src/scanner.rb:125` `collect_faces`：收集阶段先把所有候选面暂存，洞口识别延后到该层收集结束后统一做 host 匹配
- 新增私有方法 `find_host_faces(opening_face, sibling_faces)`

### 验收

- `test/test_calculator.rb` 增加一条用例：构造一个 3×3m 的墙 + 1×2m 的窗洞口，期望扣减后 `net_area = 7.0`
- 在含窗户的真实模型上，对比扣减前后的墙面面积差异日志

## P1：派生项（核心）

### 问题

现实中一张面对应一串材料：

```
墙砖饰面 → 基层处理 + 防水 + 瓷砖粘结剂 + 瓷砖 + 填缝剂
地板    → 水泥找平 + 防潮膜 + 龙骨 + 地板
吊顶    → 主龙骨 + 副龙骨 + 石膏板 + 饰面涂料
```

`calculator.rb:79` 一个 SU 材质只产出一条 usage，辅材/基层全部缺失。

### 方案

把 `ProcessLibrary` 从"替代损耗率表"扩成"派生规则表"。一条工艺 = 多条派生项，每条派生项独立配置。

**数据结构**：

```json
{
  "瓷砖": [
    {
      "process_name": "密缝铺贴",
      "derivations": [
        { "layer": "基层处理", "unit": "m²", "formula": "area",         "waste_rate": 0.02, "category": "辅材" },
        { "layer": "瓷砖粘结剂", "unit": "kg",  "formula": "area * 5",    "waste_rate": 0.05, "category": "辅材" },
        { "layer": "瓷砖",      "unit": "m²", "formula": "area",         "waste_rate": 0.05, "category": "主材" },
        { "layer": "填缝剂",    "unit": "kg",  "formula": "area * 0.3",  "waste_rate": 0.10, "category": "辅材" }
      ]
    }
  ]
}
```

### 数据模型变更

- `ProcessDef` 扩展：`Struct.new(:category, :name, :derivations, keyword_init: true)`，`derivations` 为 `Array<Derivation>`
- 新增 `Derivation = Struct.new(:layer, :unit, :formula, :waste_rate, :category, keyword_init: true)`
- `MaterialUsage` 增字段 `:layer`（派生项层名）、`:parent_su_material`（来源 SU 材质），`unit` 字段激活使用

### 代码位置

- `src/process_library.rb` 全量改造：`load_json` 适配新 schema；老 schema（仅 `waste_rate`）做兼容转换（自动包一层 `derivations: [{ layer: category, ... }]`）
- `src/calculator.rb:79` fan-out：按 SU 材质查工艺 → 每条 derivation 生成一条 `MaterialUsage`
- `data/default_processes.json` 按新 schema 重写，至少覆盖：瓷砖、地板、吊顶、涂料、石材
- `src/ui/app.js` 工艺设置页适配多派生项编辑

### 验收

- `test/test_process_library.rb` 新增用例：加载含派生项的 JSON，断言 `processes_for('瓷砖').first.derivations.size == 4`
- `test/test_calculator.rb` 新增用例：1 张 10m² 墙砖面 → 期望产出 4 条 MaterialUsage
- 在"按材料汇总"报表中能看到辅材的独立行

## P2：边长与实例计数通道

### 问题

`Scanner.collect_faces`（`scanner.rb:127`）只处理 `Sketchup::Face`。整类材料算不出来：

- **线性**：踢脚线、阴阳角、石膏线、门套（按米）
- **离散**：门、窗、开关、地漏（按个）

### 方案

让 Scanner 同时采集三种实体，并在 `ScanItem` 上打上 `kind` 标签。

**数据结构**：

```ruby
ScanItem = Struct.new(
  :face_id, :su_material, :qty, :unit, :kind,   # kind: :face / :edge / :instance
  :normal, :width, :height, :layer_name, :component_path, :z_center
)
```

`area` 改名 `qty`，语义是数量（m²/m/个），单位由 `unit` 决定。

### 实体采集规则

- **Edge**：只采集赋了材质、或位于用户指定"线性 layer 列表"（如 `踢脚线`）的边，长度 = `edge.length.to_m`
- **ComponentInstance**：按 `definition.name` 匹配 mapping 表里的条目；匹配上就作为一条 instance 产出，qty=1

### 代码位置

- `src/scanner.rb` 新增 `collect_edges` / `collect_instances` 分支
- `src/data_models.rb` 改造 `ScanItem` 结构
- `src/calculator.rb` 分组键从 `[space, part, su_material]` 扩展为 `[space, part, su_material, unit]`；不同 unit 不合并
- `src/mapping.rb` 增加 `kind` 字段约束（face/edge/instance），用于校验映射一致性
- `src/ui/app.js` 报表按 unit 分列展示数量

### 验收

- `test/test_data_models.rb` 覆盖三种 kind 的 ScanItem 构造
- 在包含踢脚线的测试模型上，报表出现"踢脚线：XX 米"独立行

## P3：损耗率升级为表达式

### 问题

固定公式 `net * (1 + waste_rate)` 无法表达：

- 地砖片数 = `ceil(area / unit_area)`
- 踢脚线长度 = `perimeter - sum(door_widths)`
- 吊顶主龙骨长度 = `area * 1.1`（间距系数）

### 方案

P1 的 `derivations[*].formula` 字段引入表达式求值。变量集合固定：

| 变量 | 含义 |
|---|---|
| `area` | 净面积 m² |
| `perimeter` | 周长 m（仅对房间级汇总有效） |
| `count` | 实例数（kind=instance 时） |
| `length` | 线长 m（kind=edge 时） |
| `unit_area` | 单片面积（spec 解析而来，如"800×800" → 0.64） |

支持运算：`+ - * /`、函数 `ceil / floor / round / min / max / sum`。

实现选项：

- **选项 A**：引入 `dentaku` gem（纯 Ruby，无依赖，~500 行）
- **选项 B**：自研极简解释器，只支持上述运算 + 函数（推荐，可控、无 gem 依赖，SketchUp 内嵌 Ruby 环境更干净）

### 代码位置

- 新增 `src/formula.rb`：`Formula.eval(expr, vars)` 返回 Float
- `src/calculator.rb` 生成 usage 时调用 `Formula.eval(derivation.formula, { area:, perimeter:, ... })`
- `test/test_formula.rb` 新建，覆盖基本运算、函数、异常处理（未定义变量、除零）

### 验收

- 测试用例：`Formula.eval("ceil(area / 0.64)", area: 10)` → `16`
- 测试用例：未定义变量抛出明确异常，不崩溃插件

## P4：规则写入模型属性字典（可选）

### 问题

规则全在 `data/*.json`，换电脑/换插件环境丢失。团队成员各算各的，结果不一致。

### 方案

仿照 `marker.rb` 的 `set_attribute` 思路，把 mapping + processes 快照写入模型级属性字典：

```ruby
model.set_attribute('su_takeoff', 'mapping',   JSON.generate(...))
model.set_attribute('su_takeoff', 'processes', JSON.generate(...))
model.set_attribute('su_takeoff', 'schema_version', 1)
```

加载优先级：

1. 模型内属性字典（跟随 .skp 文件走）
2. 插件本地 `data/*.json`（fallback）
3. 空默认值

UI 增加"快照到模型"按钮，显式写入；避免静默修改 .skp 文件。

### 代码位置

- `src/main.rb` `PluginState.load_data`：先查 `Sketchup.active_model.attribute_dictionary('su_takeoff')`
- `src/ui/dialog.rb` 新增 action callback `snapshot_to_model` / `load_from_model`
- `src/ui/app.js` 设置页增加对应按钮

### 验收

- 手动测试：A 机配置 mapping → 快照到模型 → 发送 .skp 给 B 机 → B 机打开模型 → mapping 自动加载
- `schema_version` 不匹配时给出提示，不自动覆盖

## 非目标（明确不做）

| 项 | 不做的原因 |
|---|---|
| EntityObserver 实时算量 | 与两阶段审核门禁冲突，门禁是本项目的优势 |
| BoundingBox 整栋尺寸 | 装修量粒度到房间级已足够 |
| 体积统计（m³） | 当前需求未涉及，增加复杂度收益低 |
| 通用表达式解释器（eval） | 安全风险大，P3 只做白名单函数/变量 |

## 附录 A：术语

- **毛面积**：未扣除洞口的面积
- **净面积**：扣除洞口与薄板重复面后的面积
- **派生项**：一条 SU 材质展开出的多条材料记录（主材 + 辅材 + 基层）
- **kind**：ScanItem 的量纲类型（face/edge/instance）
- **host face**：洞口所依附的母面
