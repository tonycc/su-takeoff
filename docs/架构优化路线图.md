# SU Takeoff 架构优化路线图

> 日期：2026-06-02  
> 状态：仅保留待优化项  
> 目标：在当前“几何用量统计工作台”的边界内，继续降低耦合、消除历史命名残留，并为后续按群组/组件扩展计量方式打基础。

## 1. 当前定位

项目当前定位为：

**SketchUp 几何用量统计工作台**。

核心职责：

- 扫描 SketchUp 模型中的面、群组、组件。
- 按 AttrDict 标签、图层规则、材质映射、几何启发式决议计量方式。
- 输出面积、长度、体积、件数四类几何用量。
- 支持材料映射、组件映射、忽略材料、标签规则、启发式阈值配置。
- 支持模型 AttributeDictionary 与本地 JSON 双层持久化。

当前路线图只记录仍需要优化的地方，已完成事项不再放入执行清单。

## 2. 优先级总览

| 优先级 | 优化项 | 目标 |
|---|---|---|
| P1 | 为 `face_id + component_path_ids` 增加回归测试 | 防止同定义多实例再次串计量方式 |
| P2 | `MaterialUsage` 迁移为 `GeometryUsage` | 消除历史命名，明确几何用量语义 |
| P2 | 抽出 `UnitClassifier` | 统一单位到计量方式的分类入口 |
| P2 | 处理 `default_waste_rate` 兼容字段 | 明确旧字段生命周期，避免继续扩散 |
| P2 | 清理已废弃 CSS 残留 | 删除已废弃 UI 的样式尾巴 |
| P3 | 拆分 `Scanner` | 降低 SU 运行时层复杂度 |
| P3 | 拆分 `Calculator` | 让去重、几何构建可独立测试 |
| P3 | 拆分 `model_view.js` | 降低前端维护成本 |

## 3. P1：补关键回归测试

### 3.1 同 `face_id` 不同组件路径不能串量

位置：

- `test/test_compute_geometry_only.rb` 或新增 `test/test_workbench_presenter.rb`
- `src/workbench_presenter.rb`

背景：

- 当前实现已经使用 `[face_id, component_path_ids]` 区分同定义多实例。
- 但缺少专门回归测试，后续重构 `WorkbenchPresenter` 或 `Calculator` 时容易退回只按 `face_id` 匹配。

方案：

1. 构造两个 `ScanItem.face`：
   - 相同 `face_id`
   - 不同 `component_path_ids`
   - 一个默认面积，一个带 `tags: { method: :length }`
2. 走 `WorkbenchPresenter#build`。
3. 断言两个 `geometry_usages` 分别得到：
   - 第一个 `qty_area > 0`、`qty_length == 0`
   - 第二个 `qty_area == 0`、`qty_length > 0`
   - `faces[].resolved_method` 分别为 `area` 和 `length`

验收：

- 单测能复现并锁住同定义多实例场景。
- 全量测试通过。

## 4. P2：收口几何用量数据模型

### 4.1 `MaterialUsage` 迁移为 `GeometryUsage`

位置：

- `src/data_models.rb`
- `src/calculator.rb`
- `src/workbench_presenter.rb`
- `test/test_data_models.rb`
- `test/test_compute_geometry_only.rb`

问题：

- `MaterialUsage` 这个名字来自早期按材料统计阶段。
- 当前它实际承载的是几何用量结果。
- `WorkbenchPresenter` 仍通过 `unit` 反推 method，说明结果模型没有把计量方式表达清楚。

建议模型：

```ruby
class GeometryUsage
  attr_accessor :space, :part,
                :su_material_name, :material_name,
                :category, :spec,
                :method, :unit, :quantity,
                :items, :detail,
                :confidence, :source
end
```

迁移步骤：

1. 新增 `GeometryUsage`，先让 `MaterialUsage = GeometryUsage` 兼容旧测试和调用。
2. `Calculator#compute_geometry_only` 返回 `GeometryUsage`。
3. `WorkbenchPresenter` 直接读取 `usage.method`，删除 `method_from_usage`。
4. 更新测试名称与断言，从 `MaterialUsage` 逐步迁移到 `GeometryUsage`。
5. README / AGENTS / CLAUDE 中将 `MaterialUsage` 改为 `GeometryUsage`。

验收：

- `Calculator` 输出结果中 `method` 明确存在。
- `WorkbenchPresenter` 不再通过 `unit` 推导 method。
- `rg -n "method_from_usage|MaterialUsage"` 只剩兼容别名或完全无结果。

### 4.2 处理 `default_waste_rate` 兼容字段

位置：

- `src/mapping.rb`
- `src/component_mapping.rb`
- `src/ui/dialog.rb`
- `src/ui/js/mapping.js`
- `src/ui/js/comp_mapping.js`
- `test/test_mapping.rb`
- `data/default_mapping.json`
- `data/default_component_mapping.json`

问题：

- 用户界面和几何计算链路已经不再使用损耗率。
- 映射模型、JSON、CSV 仍保留 `default_waste_rate`，目前只是旧数据兼容字段。
- 如果不明确生命周期，后续功能容易误以为损耗率仍是业务字段。

方案 A：保留兼容字段，但降级为私有遗留字段

- `MappingRecord` 内部继续读旧字段。
- 新保存 JSON 时不再主动写 `default_waste_rate`。
- CSV 导入兼容旧列，导出不再输出旧列。
- 测试改为验证“旧数据能读”，不再验证“新数据必须写”。

方案 B：完全迁移删除

- 写一次数据迁移说明。
- `MappingRecord` 和 `ComponentMappingRecord` 删除字段。
- `load_json/import_csv` 忽略旧字段。
- 所有 `waste_rate` 参数从 Ruby/JS 回调删除。

推荐：

- 先选方案 A，降低对用户已有 `data/*.json` 和 CSV 的破坏。
- 后续发布一个版本后再考虑方案 B。

验收：

- 新导出的映射 CSV 不含 `default_waste_rate`。
- 新保存的 JSON 不主动写 `default_waste_rate`。
- 旧 JSON / CSV 含该字段时仍能正常导入。
- 几何计算链路无 `waste_rate` / `default_waste_rate` 读取。

## 5. P2：统一单位分类入口

### 5.1 抽出 `UnitClassifier`

位置：

- `src/takeoff_policy.rb`
- `src/calculator.rb`
- `src/workbench_presenter.rb`
- 新增 `src/unit_classifier.rb`
- 新增或调整 `test/test_takeoff_policy.rb`

问题：

- 单位到计量方式的分类目前由 `TakeoffPolicy.classify_unit` 承担。
- `TakeoffPolicy` 同时负责策略优先级和单位词法判断，职责偏多。
- `Calculator`、`WorkbenchPresenter` 也会间接依赖这个分类逻辑。

建议接口：

```ruby
module SuTakeoff
  class UnitClassifier
    def self.classify(unit)
      # :area / :length / :volume / :count
    end
  end
end
```

迁移步骤：

1. 把 `TakeoffPolicy.classify_unit` 的实现移动到 `UnitClassifier.classify`。
2. `TakeoffPolicy` 保留一个短期兼容转发：

```ruby
def self.classify_unit(unit)
  UnitClassifier.classify(unit)
end
```

3. 项目内部调用逐步改为 `UnitClassifier.classify`。
4. 文档说明“参数管理页单位列表只影响可选项；计量分类由 `UnitClassifier` 决定”。

验收：

- 单位分类逻辑只有一个真实实现。
- 项目内部不再直接依赖 `TakeoffPolicy.classify_unit`。
- 单测覆盖 `m² / m / mm / cm / m³ / 个 / 件 / 套 / kg` 等典型单位。

## 7. P3：拆分运行时与计算大文件

### 7.1 拆分 `Scanner`

位置：

- `src/scanner.rb` 当前约 866 行。

问题：

- 一个类同时承担实体遍历、层级树构建、洞口识别、容器整体量取、线性长度计算、坐标/单位换算。
- SU API 依赖重，缺少替身测试时重构风险高。

建议拆分：

```text
src/scanner.rb
  扫描主流程与依赖组装。

src/scanner/hierarchy_builder.rb
  collect_hierarchy 相关逻辑。

src/scanner/opening_detector.rb
  透明面、门窗命名、母面关联。

src/scanner/geometry_measure.rb
  面积、bbox、体积、线性长度计算。

src/scanner/container_emitter.rb
  根据容器规则产出 solid / linear_solid / count_solid ScanItem。
```

执行顺序：

1. 先抽 `HierarchyBuilder`，只搬移层级树构建，风险最低。
2. 再抽 `OpeningDetector`，补门窗命名和透明材质测试。
3. 再抽 `GeometryMeasure`，为 `compute_linear_length` 建替身几何测试。
4. 最后抽 `ContainerEmitter`，保持容器判定顺序不变。

验收：

- `src/scanner.rb` 降到约 300 行以内。
- 容器判定顺序保持：
  1. 复合标签
  2. component mapping aggregate
  3. 标签/图层命中整体量取
  4. 正常下钻
- 线性长度、洞口关联、层级树构建均有独立测试或替身测试。

### 7.2 拆分 `Calculator`

位置：

- `src/calculator.rb` 当前约 429 行。

问题：

- `Calculator` 同时负责分组、策略决议、单位选择、水平/竖直薄板去重、几何量构建。
- 去重逻辑和几何量构建适合独立测试。

建议拆分：

```text
src/calculator.rb
  compute_geometry_only 主流程。

src/calculator/deduplicator.rb
  水平薄板、竖直薄板去重。

src/calculator/geometry_builder.rb
  area / length / volume / count 几何量构建。
```

执行顺序：

1. 抽 `Deduplicator`，保持现有测试先通过。
2. 为水平薄板和竖直薄板补边界测试。
3. 抽 `GeometryBuilder`，让不同 method 的 quantity 构建集中。
4. `Calculator` 只保留编排和分组。

验收：

- `Calculator` 主要方法可在一屏内读完。
- 去重逻辑可直接单测。
- `GeometryUsage.quantity` 对 area / length / volume / count 的来源清晰。

## 8. P3：拆分前端组件树视图

### 8.1 拆分 `model_view.js`

位置：

- `src/ui/js/model_view.js` 当前约 1255 行。

问题：

- 一个文件同时包含状态管理、树渲染、材质汇总、规格分组、定位、高亮、导出。
- 后续增加“按不同群组/组件的计量方式扩展”时，会继续加重这个文件。

建议拆分：

```text
src/ui/js/model_view.js
  入口与模块组装。

src/ui/js/model_view/state.js
  视图状态、展开状态、筛选状态。

src/ui/js/model_view/rollup.js
  组件/材质/规格汇总计算。

src/ui/js/model_view/tree_view.js
  树节点渲染。

src/ui/js/model_view/material_rows.js
  材质行与待确认状态渲染。

src/ui/js/model_view/spec_groups.js
  规格分组和面明细。

src/ui/js/model_view/export.js
  CSV 导出。

src/ui/js/model_view/formatters.js
  数值、单位、标签格式化。
```

执行顺序：

1. 先抽纯函数：formatters、rollup。
2. 再抽导出逻辑。
3. 最后拆渲染模块。

验收：

- 单个前端文件不超过约 400 行。
- `model_view.js` 只负责入口和组合。
- 扫描、展开节点、搜索、合并相同组件、定位面/组件、CSV 导出均正常。

## 10. 通用验收

每完成一个优化项，至少执行：

```bash
ruby -Itest -e "Dir.glob('test/test_*.rb').each { |f| require f.sub('test/', '') }"
```

涉及前端或 SU 运行时的优化，还需要在 SketchUp 内手动验证：

- 扫描全部。
- 扫描选中。
- 参数管理页保存配置。
- 材料映射保存/删除。
- 组件映射保存/删除。
- 忽略/取消忽略材料。
- 按组件树展开、搜索、合并相同组件。
- 定位面、定位组件。
- 同一组件定义的多个实例不会串计量方式。
